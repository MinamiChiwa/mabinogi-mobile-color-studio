# 台服、韩服客户端更新适配

精准模式从选定游戏进程的实际模块路径读取文件。旧实现只接受内置的三个文件哈希组合；台服更新后 GameAssembly 和 metadata 改变，入口因此直接拒绝。绕过版本检查也无法解决问题，因为色板类、输入类和鼠标缓存的地址同时移动了。

## 当前实现

`native_live/adaptive_build.py` 为台服、韩服共用适配入口。已登记版本保留原有适配器；未知版本先在游戏外完成以下检查，再等待活动色板：

1. 对 GameAssembly、metadata、UnityPlayer 完整取哈希。离线解析期间再次核对前两个文件的内容及修改状态，支持 F9 取消。
2. 只解析 x64、metadata v31，要求 UnityPlayer 与已有原生布局的精确哈希一致。
3. 校验 62 个读取相关类的父类和完整字段名称、类型、偏移。泛型参数按所属定义内的序号比较，不使用随构建改变的全局序号。
4. 查找唯一的色板类和输入类标记，并要求对应类自己的机器码引用该标记。鼠标缓存由 Unity 输入 getter 的引用定位；歧义结果拒绝使用。
5. 地址仅在当前工具进程的有界缓存中复用，以三个文件哈希及发现器版本为键。磁盘上的候选 JSON、会话记录和 capability 字段均不能授予输入权限。

布局契约在 `native_live/managed_layout_contract.py`，来自原台服已验证布局及韩服对照证据。它只能证明读取布局兼容，不能证明整个游戏算法等价。未知客户端不能自动覆盖这份契约。

## 当前会话的输入门槛

自动发现的适配器保持 `diagnostic_only`，不会永久晋升为 `input_verified`。用户选择台服或韩服并启动寻色后，仍须通过既有的窗口坐标、输入分支、活动色板、纹理导出、CPU 与客户端取色及稳定姿态检查。

此外，首次输入前强制读取两张完整截图，所有有效区域的屏幕 HEX 必须与当前检查点一致；原生数据补全 OCR 缺项不能满足这一步。通过后仅对当前进程、当前色板会话授予输入许可，记录为 `model_verified`。新会话、进程变化或重新选择服务器均须重新验证。

每次动作继续使用现有的输入前绑定检查和动作后姿态、取色反馈。两区、三区使用同一套验证。发现地址或首次屏幕比对通过，不代表拖动、缩放、旋转响应已经实机验收。

## 支持边界与证据

这条路径适合 Unity 版本和读取布局保持兼容、仅地址移动的客户端更新。Unity 原生布局、metadata 格式、字段契约或输入分支改变时会拒绝继续，需要人工适配。游戏算法即使未改布局也可能改变；单一姿态的取色一致无法证明全部采样和手势数学不变，后续反馈不符时仍须停止，不能承诺任何未来更新都无需维护。

2026-11-04 本机验证：更新后的台服自动发现了新地址，并通过实际进程的只读窗口与输入分支检查；本机韩服 2026-10-12 构建也由同一发现器独立找回了已知地址。韩服证据来自该本机旧构建，不能代表尚未取得的新构建。台服当前没有活动色板，因此本轮未验证真实色板的两区/三区屏幕色码及拖动、缩放、旋转、重试响应，也未发送游戏输入。
