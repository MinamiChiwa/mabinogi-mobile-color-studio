# 多服务器兼容推进计划

**目标：** 同一工具根据客户端构建自动选择适配器，支持台服、韩服以及后续同游戏服务器；不要求用户手填偏移，不改变寻色模型或时间策略。

**证据：** 用户提供 `data (4).zip`，会话 `20261011-223714-ff182c4b`。0.4.1 成功绑定韩文窗口 `마비노기 모바일`，准备阶段在 0.8 秒内报 `Unsupported game/metadata build for static object walk`；0 次输入。失败发生在构建检查之前，没有色板、截图、GameAssembly/metadata/UnityPlayer 哈希，因此不能确定韩服布局，也不能宣称已经支持。

## 方案选择

采用“构建指纹注册表＋结构发现”的组合：已验证构建使用快速适配器；未知构建通过普通游戏界面的只读诊断生成指纹和候选布局，再离线确认结构。避免按服务器名字硬编码固定偏移，也避免对未知版本直接套用台服输入逻辑。

窗口标题只做定位提示，服务器/语言只控制视觉识别资源。兼容性的实际键为：GameAssembly SHA-256、metadata SHA-256、UnityPlayer SHA-256、PE 架构、IL2CPP metadata schema、Unity 版本。GameAssembly 与 metadata 相同可以复用对象布局；UnityPlayer 单独决定屏幕/鼠标转换。所有输入前检查和实测色码复核继续保留。

## 任务及验收

- [x] 保存未知构建的三个 SHA-256；失败输出结构化 `build_diagnostic`，不暴露内部读取状态到 UI，不创建输入发送器。
- [x] 将已有台服对象入口归入 `BuildAdapter` 注册表；韩文标题加入自动窗口识别。
- [ ] 韩服普通界面只读采集：PE 架构、Unity/metadata 版本、三个哈希、模块相对名称及类名/字段摘要。只读采集不需开启染色、不消耗道具；日志不上传完整 metadata、进程内容、账号或个人路径。
- [ ] 建立离线布局发现器：按完整类名/字段类型/继承层次解析 metadata；从 code registration 关联类型入口，读取候选静态对象；不能只用字符串地址作为最终布局。
- [ ] 抽离所有构建相关布局：palette class、InputManager 静态入口、鼠标 getter、Unity screen、viewport、对象字段/数组结构与取色设置。当前注册表仅覆盖已知 palette 入口；其他模块仍为已验台服布局，未知构建不得宣称支持。
- [ ] 定义适配能力分级：`diagnostic_only`、`palette_readable`、`model_verified`、`input_verified`。自动发现只有读取能力，不能自行升级为输入可用。每级输出验证证据与原因。
- [ ] 只读色板采集验证：两次一致会话标识、2/3 区域个数、纹理大小/数组长度、矩阵有限性、实时 HEX 与重建色板相符。韩文界面数字/HEX 沿用通用识别；布局按归一化区域及实际点位绑定，拒绝依据语言猜位置。
- [ ] 普通界面预检先通过，再由用户授权一局有限道具验证；预先写好完整脚本，测试拖动、正反滚轮、有限旋转、缩小到最大范围、重试及回读，不自动确认染色。输入响应与台服模型不同则选择对应输入内核，不更改全局搜索目标。
- [ ] 将脱敏字段/最小字节片段做 fixture：相同构建不同标题、不同构建相同标题、Unity 单独升级、错误类名、字段漂移、两区/三区、DPI/尺寸与负坐标。quick 保留指纹选择/拒绝测试；实际布局与路由证据进 release，避免重复大路线回归。
- [ ] 首个韩服构建验收通过后发布适配器；未来服务器相同指纹自动复用，不同指纹走上述诊断/发现/验证。适配器由工具签名更新分发；不从网络下载并执行任意布局脚本，不允许未验证配置开启输入。

## 与自动更新的关系

适配器是应用模块和资源，随签名文件更新。更新仅安装经过维护者审核的已验证布局；不将用户测试压缩包、账号资料、完整游戏文件、私有采集或正式密钥加入仓库/发布包。韩服实际验收尚未完成，发行说明必须与台服已验证范围分开陈述。
