# 跨电脑安装路径、物理 DPI 和可变窗口布局

`用户提供的 data.zip` 内三个 rc13 会话都在预检阶段以 `Expected unique current-build UnityPlayer module` 退出，发送输入为零，没有任何窗口测量、截图或色板回读记录。这证明失败点是 UnityPlayer 模块定位，不能证明 4K 或 DPI 本身不受支持。

原 `read_unity_screen.py` 写死本机 `C:/Nexon/Library/MabinogiMobile_TW/appdata/UnityPlayer.dll`。其他模块已经按目标进程安装路径选择，但这一处残留使不同盘符/目录电脑失败。修正按目标进程真实加载路径匹配，并与该进程已校验的 build_files 绑定，支持 Unicode、路径大小写和 Windows 扩展路径；多模块或路径不一致仍拒绝。游戏/Unity DLL 和 metadata 哈希适配规则保持。

原截图预检另外限定严格 4:3、且短边至少 480，不能支持其他比例或 4K 下保持小 UI 的布局。现在先检查物理客户端尺寸合法，再以当前原生色板位置裁剪实际图片，寻找三个色码卡片和取色点，并把像素位置转换回全客户端坐标。核对卡片列中心、图片色板边界和原生矩形；原生 HEX 补缺不等于截图验证。截图里缺少色板、存在错误几何或文本/原生不一致仍不发输入。

平台层的客户端测量、截图、虚拟桌面鼠标坐标和实际输入轨迹统一使用有作用域的 PMv2 线程 DPI 上下文。每次操作后恢复调用线程原上下文，避免依赖 Tk 或打包程序已设定的进程 DPI 状态，也避免影响工具 UI 的缩放。负坐标多屏桌面也使用同一物理坐标系。

故障记录新增 `native-preparation.json`，包括失败阶段、实际安装路径、模块版本、游戏内部尺寸、物理窗口尺寸、DPI 及 viewport。在模块定位、版本适配、物理窗口测量和坐标映射失败时，界面分别说明原因，避免统一误报窗口不支持。

## 运行浮窗

用户另外要求点击游戏后浮窗仍显示，并且不影响截图或输入。浮窗使用 Win32 `HWND_TOPMOST` 及 `SWP_NOACTIVATE`，映射之后重新应用，运行心跳检查策略，避免只依赖 CustomTkinter 初次设置。原生寻色期间启用 layered/transparency 让鼠标穿透浮窗，F9 与主窗口停止仍有效；其他候选选择界面保持交互。原生流程结束仍关闭浮窗，避免此前主界面控件被终态浮窗拦截的问题。

只有 `SetWindowDisplayAffinity` 以及读回值都确认 `WDA_EXCLUDEFROMCAPTURE`，才认为窗口可以保持显示而不进入截图。未确认的窗口在采集期间暂时隐藏，完成后通过 `SW_SHOWNOACTIVATE` 恢复；已经停止/注销的窗口不被恢复。截图串行锁与 UI 注册锁分离，Win32 显隐、DWM 合成和截图过程中不阻塞 UI 注册/停止，以免工作线程和 Tk 主线程互等。

## 验证范围与边界

动态原生色板/InputGeometry 本身不限 1280×960 或 4:3。合成布局覆盖常见 4:3、16:9、竖屏及 4K 内小 UI；真实留存截图做等比缩放、不同画布比例及 UI 位置变化，属于图片回放，不是远端电脑实机证明。作用域 DPI 测试模拟继承虚拟化坐标上下文，核对物理截图边界、鼠标归一化、输入轨迹和上下文恢复。

当游戏内部 Screen 和物理客户端尺寸相同且原生输入 viewport 为已验证的 [0,0]/[1,1]，可使用当前精确输入模型。若 Windows 将游戏逻辑渲染放大成与物理客户端不同的尺寸，不能仅乘 DPI 比例：原生鼠标 getter 含 float32/floor 与 H−y−1 像素阶梯，简单倍率会改变微调路线。此类状态保存原始诊断，等待实际目标 HWND 的坐标/事件映射证明后适配；不会猜测错误坐标点击。需要先在另一台电脑做只读预检，不必进入染色或消耗道具。

本次在本机现有游戏进程执行只读预检，通过；没有激活、调整游戏窗口、发送输入或消耗新道具。上传诊断文件仅按数据读取。
