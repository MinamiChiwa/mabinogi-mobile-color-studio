# rc8 双黑失败审计与 rc9 候选验证

日期：2026-10-10。候选：0.4.0rc9，策略修订号 `native-periodic-streamed-v7`。

## 已观察事实

失败会话 `20261010-151149-fd4e2d56` 实际运行 rc8，前两区精准 `#000000`、第三区禁用。会话记录、发布包 manifest 和包内关键模块匹配，因此不是旧包或入口接错。入口为 App → Runner native → native_live.service → controller → same_session_dye_planner → native_periodic_search / native_input_pipeline。

周期搜索识别到前两区各 475 个黑色采样点。在 2.5 秒固定子阶段期限内，它先枚举所有配对，再验证候选；本次配对枚举未结束，CPU 候选校验数为 0。后续路线搜索因此没有拿到周期双黑目标，选中了不含旋转的妥协路线。最终实机回读 `#241410 / #1D1000`，ΔE76 为 12.44 / 11.04。这不能作为色板无解的证据。

本局确实只进行了一轮规划，然后依次执行五个手势；“未连续”的主要表现是动作间长停顿。事件记录中的动作间隔约为 3.86、9.08、3.81、4.56 秒，完整流程耗时 50.47 秒。每个中间动作后都重新做稳定检查、导出色板与双帧截图/OCR；原生姿态响应与预测相符，未因偏差触发重复搜索。

## 保存数据可证明的内容

使用原 rc8 包内周期搜索，在充足离线时间下约 2.9 秒得到 32 个 CPU 精确双黑姿态。把这些姿态传入已有 native_input_pipeline，生产 shortlist 16 的路线搜索约 4 秒生成包含旋转的精准双黑路线。因此本局失败来自搜索阶段饥饿，而不是缺少旋转支持或目标不存在。

独立搜索也发现不旋转的模型双黑姿态及滚轮路线。旋转是否出现不能单独判断策略是否接入；应检查目标规则、周期候选、路线端点评分和实际回读。

## 修正

- 配对计算按两维分块，最大每块 32 × 1024 个配对；产生候选后立即用原 float32 CPU 模型校验。期限中断保留已验证候选，不再把全枚举放在首次校验之前。仍扫描一个周期、游戏倍率范围和完整旋转范围；有限候选保留池及采样格点不代表连续空间穷尽。
- 保持整条已验证路线逐手势执行。中间步骤读取绑定、稳定的原生姿态和实际客户端色码；入口、输入前初次复核、终点、提前命中或响应偏差时做双帧视觉读取。取消、失焦和绑定改变仍会停止输入。
- 小旋转偏差后从实际姿态重算剩余动作，只有剩余端点仍满足原精准规则才继续。没有放宽颜色容差，也没有用 `#010101` 代替纯黑。
- 双阈值截图字形且色块匹配时直接读码；不确定卡片仍走原 OCR。原生补值与截图独立证据分别标记，补值不能伪装成截图确认。
- 界面事件单项渲染或历史写入异常不会停止后续轮询，`finished` 仍会恢复控件。旧实机按钮失效的具体触发原因没有确证；此次只修复已复现的异常阻断轮询路径。先前“大 JSON 导致按钮失效”的判断证据不足。
