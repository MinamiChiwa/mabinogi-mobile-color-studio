现有两局资料不能唯一确定游戏内部的纹理取样规则；以下把测得事实、排查结果和待验证假设分开记录。

## 已找到的答案

### 可见圆心确有亚像素偏差

当前识别器固定使用色卡整数中心 x，并以整数 y 搜索白色圆环。用训练帧中稳定的白色圆环拟合圆心、排除顶部引导线，在多个亮度门槛下测得新局相对当前坐标的近似修正为：

|区域|dx|dy|
|---|---:|---:|
|1|−0.661|+0.307|
|2|−0.310|+0.012|
|3|+0.105|+0.719|

这些拟合不使用游戏 HEX。它们描述可见 UI 圆环，不证明游戏内部实际取色点恰好位于该中心。

原生训练帧取样的检查：新局 `grid_012` 区域 3 从 `#69657D` 调整到 `#5A6785`，与游戏 `#5A6684` 的 ΔE76 从 **6.73 降到 0.49**。旧局 `grid_012` 区域 2 从 **19.55 降到 11.95**。圆心误差确实能解释一部分问题。

但新局 `grid_030` 区域 2 仍从 **35.21 仅降到 25.86**，不支持“改圆心即可完全解决”。尚未将这组本局拟合数字写入生产识别器。

### 局部配准有贡献，但不是两处最大异常的主要原因

对每个留出取色点周围半径 42 像素的可见纹理，与原生训练图重新配准。圆圈、线和材质边界全部排除；对所有候选偏移使用共同有效像素。先在 ±1.5 像素按 0.25 步长搜索，再在最佳附近按 0.05 步长细化。损失不使用色卡或游戏 HEX。

- 新局 `grid_030` 区域 2 对两张训练图，各使用 4604 个可见像素。最佳修正均约 **(0,+0.05)** 像素，点位 ΔE76 仍约 **35.69 / 36.99**。支持邻近纹理已经基本对齐，不能用一像素级局部错位解释该异常。
- 旧局 `grid_012` 区域 2 最佳修正约 **(−0.05,+0.05)**，色差仍 **19.92**。
- 旧局 `grid_036` 区域 2 则测到约 **(−0.55,−0.40)** 的修正，局部纹理 RMSE 从 **11.51 降到 8.17**，点位色差从 **7.24 降到 4.73**。说明部分位置的局部配准确实还需要改进，不能笼统宣称所有配准都没有问题。

此搜索是利用留出可见纹理进行的诊断，不是对生产模型的新独立验收，也没有使用它修正生产偏移。

### 放大前的截图同样复现异常

把保存的 `original_board.png` 与 `max_sampling` 图像配准，测得新局跨尺度比例约 1.612，257 个内点。使用未进入 atlas 建图的放大前截图，检查同一个 `grid_030` 第二区域纹理位置：

- 原坐标预测 `#9C7978`，游戏 `#946531`，ΔE76 **31.34**。
- 应用独立圆环几何修正后，预测 `#99736B`，ΔE76 **26.54**。

因此异常不是 768 atlas 这一次重采样单独造成的；不同倍率的截图预测也有同类偏差。跨尺度配准本身还有误差，这项检查不能单独证明渲染器使用了哪一种插值算法。

## 没有得到支持的简单解释

1. **固定圆心偏移解释一切**：此前仅训练色卡拟合的固定偏移仍留下很大的留出误差，本次独立圆环几何测量也一样。
2. **CPU 只是取最近纹理格点**：对多种候选纹理格点密度测试最近格点模型；只用训练帧色卡选择格点密度和原点，再检查留出帧。新局第二区域最佳训练模型在 `grid_030` 留出点仍约 ΔE76 28，且不同区域/会话选择的格点密度不一致。不能据此宣布游戏使用 nearest，也不能把拟合出的数字当成真实纹理尺寸。
3. **周期内坐标存在简单线性偏差**：在几何圆心修正基础上，只用训练色卡拟合常量、分轴缩放和二维仿射修正。新局异常仍约 ΔE76 20；旧局主要异常没有稳定改善。局部优化不能排除所有非线性模型，但没有找到可推广的简单坐标补丁。

## 仍缺少什么证据

需要区分的是：取色点真正的内部坐标/UV 约定、游戏色码的取样规则、以及截图渲染与后续插值造成的信息损失。

现有两局的大部分平移是整数像素；同一细色带的亚像素观测不足，而且真正被取色的位置被圆圈覆盖。即使不同训练帧得到接近的 RGB，也可能重复观察同一种像素相位。现有资料不足以唯一反推出被遮挡位置的连续颜色函数。

已确认 atlas 重采样会提高整板 RMSE；**尚不能宣称剩余 HEX 异常已经确定是某一种渲染插值、某个纹理尺寸或某个固定偏移**。最大倍率也无法从已经在第 48 步停止的历史采样推断。

## 已准备的最小新实验

入口：`run_point_probe.bat`；底层为 `live_atlas_capture.py --strategy probe` 与 `point_sampling_probe.py`。

目的：在同一条细色带附近取得一串实际小于一像素的位移、对应原生截图和游戏色码，观察颜色随连续位置如何变化。它不会进行完整 atlas 扫描或候选定位。

流程：

1. 严格检查 OCR，等待用户手动进入倒计时；沿用原有真实倒计时、焦点、窗口几何、停止和 F9 保护。
2. 使用现有 48 步有界放大，不把它称为最大倍率。
3. 在区域 2 可见、未被 UI 遮挡的位置选取细色带；保留参考图，然后只做一次整数定位。
4. 对两个略有不同的鼠标支点执行放大一格/缩小一格，尝试产生很小的平移；横纵各 8 次，共最多 16 次配对探测。
5. 每次从截图测量实际运动。只有约 0.06–1.00 像素的位移且倍率、角度基本不变才继续；无位移、配准失败或缩放未恢复均立即停止。指令本身不算测量结果。
6. 点位阶段硬截止为 **25 秒**，还受原始倒计时预留限制；这不包括等待和初始放大，也不是已经实测的完成时间。
7. 保存 `probe_000` 到最多 `probe_016` 的全图、板图、参考图、支点、位移矩阵和时间。结束后由用户处理游戏退出，不点击确认、套用、取消或再次开局。

该办法使用项目已有的“滚轮围绕鼠标位置缩放”操作模型；本次配对微移尚未经过实机验证。如果实际游戏不支持这样的微移，将保留失败现场并停止，不自动改做其他输入或再次尝试新局。

点位采样目录被 atlas 分析器明确拒绝，不能误当成完整图板生成候选。正式 UI 的默认网格、768 分辨率和质量门槛没有改变。

用户操作：保持客户区 1280×960，运行 `run_preflight.bat`，通过后运行 `run_point_probe.bat`；看到“等待用户手动进入…”再手动进入一次倒计时。发生中止也保留日志，**不要重复开局**。

后续判别：离线读取新截图的游戏 HEX，在共同几何坐标下比较连续取样、格点跳变和局部颜色变化；必要时用部分微移点标定，其余点验证。配对微移若失败，先分析实际运动和失败原因，不把无效数据用于猜测引擎行为。
