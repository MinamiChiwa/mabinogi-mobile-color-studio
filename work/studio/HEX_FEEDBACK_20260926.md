## 1. 截图是否普遍损失颜色

自建 `capture_color_check.py` 显示 2048 个确定 RGB 色块，包含全部 256 级灰阶、
红/绿/蓝单通道渐变、历史异常暗色和固定种子随机颜色。测试图 1024×512，
在 DPI 96 下以 1:1 像素显示；采集前检查前台窗口、显示尺寸和九点遮挡。
截图使用与生产相同的 `PIL.ImageGrab.grab(all_screens=True).convert('RGB')` 路径。

初始差异集中在色块图底部少量像素，拉开交互区后消失，符合局部界面/指针视觉干扰的可能性；
尚未独立证明具体来源，没有放宽阈值、裁掉异常像素或修改颜色后再比较。

**结论：** 当前证据不支持截图 API 或 PNG 保存普遍劣化颜色来解释游戏内的大色差。
这一结果只验证当前桌面的 Tk/SDR 标准色块，不认证游戏的 HDR、交换链、着色器和内部取样规则。
此前暗色色卡的量化现象与 atlas 点位预测错误仍是游戏画面层的独立问题。
暂不因“截图劣化”更换采集 API；算法主线改为使用游戏 HEX 对结果闭环核验。

## 2. 六十秒如何落到代码

- `workflow_budget.py` 从识别到可靠染色界面的 `ready_at` 开始计时，手动等待不计入。
- 游戏真实截止取两次 OCR 及各自截图时刻所得截止的较早者，不用假定 120 秒。
- 有效截止为 `min(ready_at + 60, game_deadline)`，采样截止为有效截止减十二秒。
  十二秒只是最低后处理预留，尚不是建图、候选、微调足够快的证据。
- `CaptureGame` 分开保存全程截止和采样阶段截止。采样完成只解除阶段上限，不能延长全程截止。
  点位 probe 仍另有限制为最多二十五秒，且不能越过其他更早截止。
- 实际输入发送前再次检查 F9、失焦、几何与截止，封住基础鼠标路径短暂等待后的输入空隙；
  到期或停止后的释放按钮仍允许发送。
- 建图在阶段间检查保护，前后再次检查截止；候选计算返回后也检查。
  超时不得发布可选候选或开始默认定位。上下文覆盖只能缩短报告与批次截止。
- 用户二次选择仍以同一截止预算预检；过期不能创建可执行的新截止。

这是输入/发布保护，不是硬实时 CPU 调度：单次同步图像计算可能到下一检查点才返回，
但不能在检查失败后继续执行定位。尚未声称所有后台计算也严格在第六十秒退出。

**现有链路未达标：** 新完整局的 ready→采集结束为 56.84 秒，建图约 11.92 秒，
二者已达 68.76 秒，且不包括候选定位与 HEX 修正。39 次拖动和正式质量门槛未改；
新保护可能在扫描完成前安全中止。现在不要用新染色剂重复旧扫描。

## 3. HEX 修正原型的范围

`hex_refinement.py` 是平台无关、未接入正式入口的有限搜索控制器：

1. 从当前粗定位点开始，连续两次读取全部启用区域的 HEX，要求稳定。
2. 按所有启用区域的容差归一化误差排序，保留原有精准/相似模式接受条件。
   容差内仍继续改善；只有所有启用区域命中某个目标原色才提前完成。
3. 在有限半径中按轴向邻域搜索，每步移动都用图像配准测实际位移，
   同时检查与参考图累计位移是否一致。发出移动命令不等于已到达。
4. 显式限制尝试数、单次命令、定位步数、搜索范围和截止，并为返回和复核保留时间。
5. 探索后回到历史最佳点，再复核启用区域 HEX 是否重现。
   保护、OCR、配准失败立即停止；不盲目返回，不把历史最佳冒充当前位置。

当前默认 0.25/0.125 像素邻域、2 像素半径、十二次尝试，以及每试两秒/返回三秒/
验证一秒，**全部是离线原型参数，未在游戏标定**。真实微移实验出现累计比例变化，
不能直接将配对滚轮视为纯平移适配器。跨越较大缩放变化必须中止并重新建立几何依据。

模拟覆盖：移动不足时反馈修正、三区域共同评价、精准不接受近色、容差内继续改善、
返回最优并验证、短预算不探索、过期不输入、缺失/不稳定 OCR、零移动、停止、
上下文变化、缩放变化、动作超时和返回时 HEX 不复现。
这些检查验证控制逻辑，不证明真实配准具有 0.035 像素精度，也不证明真实回退可行。
